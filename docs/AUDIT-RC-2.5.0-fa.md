# ممیزی آزمون نسخه 2.5.0-rc.1

> بسته آزمایشی تازه **2.5.0-rc.2** با اصلاحات ساخته و صحت آرشیو بررسی شد: ۵۶۷ بررسی PHP، ۱۷ تست JavaScript و نحو ۲۴ فایل runtime موفق. [ثبت ساخت و checksum](RC2-BUILD-fa.md) · [چک‌لیست نصب واقعی](RC-2.5.0-rc.2-fa.md). عبارت‌های «ZIP بازسازی نشده» در یادداشت‌های مراحل زیر تاریخی‌اند؛ RC1 همچنان همان بسته قدیمی است. تأیید تولید صادر نشده است.

> مرحله نهم: A09 (تلاش دوباره جزئیات محصول لینک مستقیم) اصلاح و bundle فروشگاه بازسازی شد؛ ۱۷ تست JavaScript و ۵۶۷ بررسی PHP موفق‌اند. [جزئیات](FIX-A09-fa.md). ریسک timeout مبهم شبکه و آزمون زنده باقی‌اند؛ ZIP تاریخی بازسازی نشده است.

> مرحله هشتم: A08 (ناپدیدشدن صفحه‌بندی در صفحه خالی) اصلاح و bundle فروشگاه بازسازی شد؛ ۱۳ تست JavaScript و ۵۶۷ بررسی PHP موفق‌اند. [جزئیات](FIX-A08-fa.md). A09 و ریسک timeout مبهم شبکه باقی‌اند؛ ZIP تاریخی بازسازی نشده است.

> مرحله هفتم: تکرار ناشی از شکست checkpoint صف در RC08 با وضعیت پایدار uncertain مهار شد؛ ۵۶۷ بررسی PHP و ۹ تست JavaScript موفق‌اند. timeout مبهم شبکه همچنان ریسک باز است و exactly-once تضمین نمی‌شود. [جزئیات](FIX-RC08-fa.md). ZIP تاریخی بازسازی نشده است.

> مرحله ششم: RC05 (اعلام موفقیت با وجود شکست ذخیره لینک مدیر) اصلاح شد؛ ۵۵۹ بررسی PHP و ۹ تست JavaScript موفق‌اند. [جزئیات](FIX-RC05-fa.md). بسته ZIP تاریخی هنوز بازسازی نشده است.

> مرحله پنجم: RC04/RC04b (تاریخ تقویمی نامعتبر روزانه/هفتگی) اصلاح شدند؛ ۵۴۸ بررسی PHP و ۹ تست JavaScript موفق‌اند. [جزئیات و محدودیت بازیابی](FIX-RC04-fa.md). نام سازنده نیز به استودیو جادید با نشانی javiiid.ir تغییر کرد. ZIP و شواهد تاریخی زیر به‌روز نشده‌اند.

> مرحله چهارم: تولیدکنندگان پاسخ تازه ربات به نوع صریح، مهلت ۱۵دقیقه‌ای و کنترل مجوز منتقل شدند (RC03). پیام‌های قدیمیِ بی‌نوع آزاد نشده‌اند. اکنون ۴۷۹ بررسی PHP و ۹ تست JavaScript موفق‌اند؛ [جزئیات](FIX-RC03-fa.md). گزارش و بسته تاریخی پایین شامل این اصلاح نیستند.

> مرحله سوم: RC01/RC02 (از دست رفتن نوع پیام در fallback و checkout) اصلاح شدند. ۴۵۲ بررسی PHP و ۹ تست JavaScript موفق‌اند. RC03 برای پاسخ‌های از ابتدا بی‌نوع همچنان باز است؛ محافظ قرنطینه حذف نشده. [جزئیات](FIX-RC01-RC02-fa.md). ZIP و شواهد تاریخی زیر مربوط به قبل از این اصلاح‌اند.

> مرحله دوم: RC06 با مقیدکردن grant و توکن به نسخه مالک اصلاح شد؛ ۴۲۴ بررسی PHP و ۹ تست JavaScript موفق‌اند. اتصال‌ها/توکن‌های قدیمی فاقد نسخه معتبر نیستند. [جزئیات و محدودیت‌ها](FIX-RC06-fa.md). اعداد و یافته‌های تاریخی پایین وضعیت پیش از اصلاح را نشان می‌دهند. ZIP قبلی به‌روز نشده است.

> به‌روزرسانی اصلاح مرحله اول: کنترل مقصد `admin_order` برای RC07 اضافه و با ۱۸ بررسی regression آزموده شد. اکنون ۴۰۷ بررسی PHP و ۹ تست JavaScript موفق‌اند. جزئیات و مرز هم‌زمانی در [اصلاح RC07](FIX-RC07-fa.md) آمده است. یافته‌ها، اعداد و هش ZIP در متن پایین مربوط به ممیزی پیش از این اصلاح‌اند؛ بسته RC1 بازسازی نشده است. سایر یافته‌ها هنوز باز هستند.

## نتیجه اجرایی

**بسته فعلی برای نصب روی سایت اصلی تأیید نمی‌شود.** تست‌های عادی موفق‌اند، اما سناریوهای تزریق خطا و تغییر مجوز، ایرادهایی را نشان دادند که در تست‌های عادی پوشش داده نشده بودند.

در این نوبت کد اجرایی افزونه تغییر نکرد؛ سه فایل آزمون بازتولید و یک runner ممیزی اضافه شدند. ZIP از سورس موجود دوباره ساخته شد و SHA-256 آن دقیقاً با manifest قبلی یکسان بود. بنابراین این گزارش مربوط به همان بسته تحویلی است، نه نسخه‌ای با اصلاحات پنهان.

این گزارش ادعای بررسی معنایی تک‌تک کلمات یا اجرای صددرصد خطوط/شاخه‌ها ندارد. «تست کلمه‌به‌کلمه» معیار قابل اندازه‌گیری نیست. هر فایل PHP از نظر نحو بررسی شد؛ بررسی رفتاری از طریق تست‌ها و مرور مسیرهای مشخص انجام شد. درصد line/branch coverage اندازه‌گیری نشده است. هیچ ادعایی درباره رخداد افشا روی سایت‌های فعلی کاربر وجود ندارد.

## ۲. یافته‌های بازتولیدشده

### RC01 — متوسط/زیاد: از دست رفتن نوع پیام هنگام خطای شبکه

**محل:** `class-bon-api.php:54,67` و guard پیام بدون نوع در `class-bon-queue.php`.

آزمون، `send_message` را با نوع صریح `admin_order` و بدون شناسه سفارش فراخوانی می‌کند. خطای مصنوعی شبکه ایجاد می‌شود. API نتیجه `queued` می‌دهد ولی fallback نوع پیام را به enqueue منتقل نمی‌کند و ردیف با نوع خالی ساخته می‌شود. worker فعلی ردیف خالی را به‌دلیل سیاست مهاجرت متوقف می‌کند.

**دامنه:** همه اعلان‌های مدیر خراب نیستند؛ مسیرهایی که با شناسه سفارش پیشاپیش وارد صف می‌شوند این شاخه را طی نمی‌کنند. مسئله مخصوص fallback بدون order_id و پیام‌های مشابه است.

**پیشنهاد:** قرارداد واحد برای order_id/message_type در request و تمام مسیرهای صف؛ تست end-to-end API→queue→worker، نه فقط mock جداگانه هر بخش.

### RC02 — متوسط: از دست رفتن نوع در شاخه تراکنشی

**محل:** `class-bon-api.php:101–102`.

وقتی ارسال در context یکی از hookهای checkout رخ دهد و order_id صفر باشد، شاخه تراکنشی نیز نوع صریح ورودی را کنار می‌گذارد. fixture context هوک را فعال کرد؛ ردیف بی‌نوع ایجاد شد و با سیاست worker ناسازگار است.

این یک شرط لبه‌ای است، نه اثبات خرابی مسیر عادی اعلان سفارش جدید که order_id مثبت می‌فرستد. ریشه آن با RC01 مشترک است؛ دو ریشه مستقل امنیتی شمرده نمی‌شوند.

### RC03 — متوسط: صف پاسخ‌های کوتاه ربات با قرنطینه مهاجرت ناسازگار است

**محل:** `class-bon-api.php::send_message/request` و `class-bon-queue.php::process_queue`.

پاسخ‌های مستقیم بدون نوع، هنگام خطای موقت وارد صف بدون نوع می‌شوند. ردیف قدیمیِ بی‌نوع و ردیف تازه یکسان دیده می‌شوند؛ worker هر دو را متوقف می‌کند. وجود fallback به‌تنهایی به معنی تلاش مجدد مؤثر نیست.

**پیشنهاد:** نوع صریح برای پاسخ‌های تازه و سیاست اعتبارسنجی مقصد/انقضا، بدون بازکردن مجوز تمام ردیف‌های قدیمی. حذف کور guard مهاجرت راه‌حل امنی نیست.

### RC04 — متوسط: مقدار تاریخ نامعتبر می‌تواند در init استثنا ایجاد کند

**محل:** `class-bon-cron.php:40–42,87–92`.

regex صرفاً شکل `YYYY-MM-DD` را بررسی می‌کند. مقدار ذخیره‌شده مصنوعی `2026-99-99` از این فیلتر می‌گذرد اما `DateTimeImmutable` استثنا می‌دهد. هر دو مسیر روزانه و هفتگی بازتولید شدند.

**شرط وقوع:** داده گزینه باید خراب، دستی ویرایش‌شده یا از مهاجرت/بکاپ ناسازگار باشد. این مسیر اثبات حمله عمومی ناشناس نیست. چون متد روی init ثبت شده، دامنه اختلال می‌تواند از خود صفحه گزارش بیشتر باشد.

**پیشنهاد:** اعتبارسنجی واقعی تقویم با تطبیق round-trip، رسیدگی به مقدار خراب بدون استثنای کنترل‌نشده و ثبت هشدار قابل اقدام.

### RC05 — متوسط: شکست ذخیره درخواست اتصال مدیر بازخورد درست ندارد

**محل:** `class-bon-admin-link.php:31–33`.

در fixture، transient ساخته می‌شود ولی `update_user_meta` شکست می‌خورد. handler همچنان پیام عادی اعتبار ده‌دقیقه‌ای لینک را نشان می‌دهد؛ صفحه بعد نمی‌تواند توکن را از user meta پیدا کند و درخواست یتیم باقی می‌ماند.

این مورد **اعطای مجوز بدون تأیید نیست**؛ خرابی گردش‌کار و بازخورد است.

**پیشنهاد:** نتیجه هر دو ذخیره خوانده و تطبیق داده شود؛ در شکست، transient یتیم پاک و خطای قابل فهم نمایش داده شود.

### RC06 — زیادِ مشروط: تغییر مالک سفارش، مجوز چت قبلی را باطل نمی‌کند

**محل:** `class-bon-customer-store.php:43–65` و مصرف‌کنندگان `owns_order`.

یک سفارش برای مشتری Alice به چت 42 متصل شد. سپس مدل سفارش در fixture به مشتری Bob و ایمیل متفاوت تغییر کرد. `owns_order` همچنان چت 42 را مجاز دانست، چون grant فقط order_id و chat_id دارد و وضعیت مالک را بررسی نمی‌کند.

اتصال سفارش‌محور قبلی جلوی دسترسی به **سفارش دیگر با همان تلفن** را می‌گیرد؛ این اصلاح نقض نشده است. مسئله تازه/باقی‌مانده **تغییر صاحب همان سفارش** است. وقوع انتقال مالک در سایت واقعی شرط اثر است.

**پیشنهاد:** سیاست صریح ابطال grant هنگام انتقال مالک، یا ذخیره نسخه/اثر انگشت هویت مالک هنگام اتصال و بازبینی آن. تغییر ساده یک نشانی یا اصلاح تایپی را نباید بدون طراحی تجربه کاربر معادل انتقال مالک گرفت. سفارش مهمان، بازیابی بکاپ و HPOS جدا آزموده شوند.

### RC07 — زیادِ مشروط: پیام صف‌شده مدیر حذف‌شده همچنان ارسال می‌شود

**محل:** `class-bon-queue.php:80–136`.

مقصد فعلی مدیران فقط 99 بود؛ یک پیام `admin_order` برای مقصد سابق 42 در صف قرار داشت. worker واقعی افزونه با transport مصنوعی به 42 ارسال کرد و ردیف را sent کرد. انواع گزارش روزانه و رونوشت پشتیبانی guard اختصاصی دارند، اما `admin_order` چنین بازبینی‌ای ندارد.

**اثر:** حذف مدیر/گیرنده از پنل لزوماً پیام‌های سفارشِ از قبل صف‌شده را متوقف نمی‌کند. این ادعای رخداد واقعی در سایت نیست.

**پیشنهاد:** اعتبارسنجی مقصدهای مدیریتی همه انواع پیام هنگام تحویل، همراه با هماهنگی تغییر مجوز و worker. شناسه شخص مجاز با مقصد گروه/کانال یک مفهوم واحد نیست؛ قراردادشان باید روشن باشد.

### RC08 — زیاد برای قابلیت اتکا: پذیرش API و شکست checkpoint باعث تکرار می‌شود

**محل:** `class-bon-queue.php:147–156` و مسیر ثبت قطعه پیام.

API مصنوعی موفق بود، ولی update نهایی `status=sent` عمداً شکست خورد. اجرای بعدی worker همان پیام را دوباره ارسال کرد. در پایان دو فراخوانی ارسال ثبت شد و ردیف هنوز pending بود. این همان محدودیت قبلاً مستندشده است که اکنون با اجرای مسیر واقعی worker بازتولید شد.

همچنین نتیجه update پیش از ثبت لاگ موفقیت بررسی نمی‌شود؛ وضعیت دیتابیس و متن لاگ می‌توانند با هم ناسازگار باشند.

**پیشنهاد:** تشخیص حالت مبهم و checkpoint ناموفق، بازخورد صادقانه و سیاست بازیابی کنترل‌شده. تضمین exactly-once صرفاً با افزودن یک پرچم محلی ممکن نیست؛ در گم‌شدن پاسخ API، قرارداد idempotency سمت سرویس لازم است.

## ۳. دو ایراد رابط که همچنان باز هستند

- **A08:** وقتی صفحه اول فیلتر محصول خالی است ولی صفحه بعد وجود دارد، pagination نمایش داده نمی‌شود. محل: `commerce-ui/src/main.jsx:84–87`.
- **A09:** پس از خطای دریافت جزئیات محصول از لینک مستقیم، «تلاش دوباره» درخواست کاتالوگ را تکرار می‌کند، نه همان جزئیات محصول. محل: effect جزئیات و دکمه retry در `main.jsx`.

هر دو روی bundle موجود با jsdom دوباره بازتولید شدند؛ نه روی مرورگر زنده یا وب‌ویوی بله.

بررسی کد همچنان ریسک‌های قبلی ثبت اعلان زودهنگام سفارش، هم‌زمانی کانال و کنترل نتیجه ساخت جدول را نشان می‌دهد؛ در این دور دوباره به‌عنوان یافته جدید با آزمایش زنده شمارش نشده‌اند. متن «سابقه سابقه گزارش‌ها» در عنوان پنل نیز ایراد ظاهری کوچک است، نه مشکل امنیتی.

## ۵. چرا ۳۸۹ بررسی موفق، این ایرادها را نشان نداده بود؟

بسیاری از تست‌ها یک کلاس واقعی را با همکاران شبیه‌سازی‌شده اجرا می‌کنند. مثلاً تست API می‌تواند فقط enqueue موفق را ببیند و تست worker فقط پیام نوع‌دار را دریافت کند؛ ناسازگاری نوع خالی بین این دو در تست یکپارچه آشکار می‌شود. همچنین تست تغییر مشتریِ همان سفارش و شکست `user_meta` در مجموعه قبلی وجود نداشت. این شکاف‌ها باید پس از اصلاح به regression دائمی تبدیل شوند.

عدد بررسی‌ها با line coverage یا تعداد سناریوهای مستقل امنیتی برابر نیست. در ممیزی worker، ۲۴ بررسی fixture قبلی نیز اجرا می‌شود؛ آن ۲۴ مورد دوباره به ۳۸۹ اضافه و به‌عنوان پوشش تازه شمرده نشده‌اند.

## ۶. اجرای دوباره

```bash
PHP_BIN=/path/to/php tests/run.sh
npm ci --prefix commerce-ui
npm test --prefix commerce-ui
PHP_BIN=/path/to/php bash scripts/run-rc-audit.sh
npm audit --prefix commerce-ui --omit=dev
python3 scripts/package-rc.py
```

سه harness تازه خارج از runner معمول‌اند:

- `tests/audit-rc-api.php`: سه مشاهده نوع پیام/fallback.
- `tests/audit-rc-state.php`: چهار مشاهده تاریخ، اتصال مدیر و انتقال مالک.
- `tests/audit-rc-worker.php`: دو مشاهده مقصد مدیر و checkpoint؛ ابتدا fixture روزانه را اجرا می‌کند.

**موفقیت harness ممیزی یعنی رفتار نامطلوب بازتولید شده، نه اینکه رفع شده است.** ممیزی‌های PHP قدیمی `audit-deep.php` و `audit-known-issues.php` با مدل اتصال و قراردادهای جدید هماهنگ نیستند؛ در این دور به‌عنوان معیار قبولی جاری اجرا نشدند.
