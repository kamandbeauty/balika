# اصلاح مرحله ششم: تأیید ذخیره لینک اتصال مدیر (RC05)

ساخت لینک اکنون دو readback دارد: ابتدا درخواست موقت با شناسه مدیر و انقضای ده‌دقیقه‌ای باید دقیقاً قابل خواندن باشد؛ سپس اشاره‌گر توکن در user meta باید با توکن جدید برابر باشد. فقط پس از هر دو تأیید پیام لینک ساخته‌شده نمایش داده می‌شود. شکست هر مرحله پیام خطای قابل تلاش مجدد دارد و پاک‌سازی درخواست جدید انجام می‌شود.

درخواست قبلی پیش از ذخیره موفق جایگزین حذف نمی‌شود. اگر پاک‌سازی transient شکست بخورد، درخواست یتیم یا جایگزین‌شده نمی‌تواند صرفاً به اتکای وجود transient پذیرفته شود: هنگام دریافت پیام بله (قبل و داخل قفل)، تأیید در پنل و نمایش لینک، توکن باید اشاره‌گر فعلی همان مدیر باشد و هنوز منقضی نشده باشد. تأیید دومرحله‌ای و تطبیق حساب نمایش‌داده‌شده حفظ شده‌اند؛ دریافت پیام بله به‌تنهایی دسترسی نمی‌دهد.

## آزمون

۱۱ بررسی تازه در tests/admin-pair-persistence.php: شکست ذخیره transient و user meta، شکست جایگزینی با حفظ لینک قبلی، readback موفق با return=false، شکست پاک‌سازی و رد توکن یتیم/قدیمی، انقضا و تکمیل تأیید دومرحله‌ای.

مجموع **۵۵۹ بررسی PHP و ۹ تست JavaScript موفق**؛ ممیزی RC05 اکنون پیام خطا و پاک‌شدن درخواست ناقص را بررسی می‌کند. نحو سه فایل PHP این مرحله با parser PHP 7.4 بررسی شد.

## محدودیت

ذخیره transient و user meta تراکنش اتمیک مشترک ندارند. این اصلاح رفتار شکست ذخیره و استفاده از درخواست یتیم را پوشش می‌دهد، نه اثبات اتمیک‌بودن تمام درخواست‌های هم‌زمان. تست با DB/cache مصنوعی انجام شده، نه WordPress/MySQL/object-cache زنده. ZIP قبلی بازسازی نشده است.

موارد باقی‌مانده ممیزی: RC08 (تحویل نامشخص/ثبت وضعیت ارسال)، A08 و A09 (رابط محصولات).
