# ممیزی تکمیلی بالیکا — وضعیت فعلی پس از حذف بله‌پی

> این گزارش مربوط به قبل از افزودن صندوق پشتیبانی انسانی است. قابلیت جدید و محدودیت‌های آن در [راهنمای پشتیبانی](SUPPORT-fa.md) آمده است؛ ایرادهای سفارش و صف عمومی همچنان باز هستند.

> به‌روزرسانی قدم اول پنل: D04/D05 در handler تنظیمات اصلی و B01 (شمارش درج موفق، مقصد یکتا و بازپخش همان فرم) اصلاح و در `tests/settings-safety.php` پوشش داده شده‌اند. جزئیات تاریخی پایین مربوط به قبل از اصلاح است. تست قدیمی `tests/audit-deep.php` برای این مسیرهای تغییرکرده دیگر معیار جاری نیست؛ آزمون جدید در runner اصلی قرار دارد. سایر یافته‌ها با این مرحله بسته نشده‌اند.

## نتیجه اصلی

**کد فعلی هنوز برای اعلام «بی‌باگ و آماده انتشار عمومی» مناسب نیست.** این دور، شش یافته تازه را با اجرای متدهای واقعی افزونه روی محیط شبیه‌سازی‌شده بازتولید کرد. سه سناریوی مشکل پیام انبوه که قبلاً فقط از روی کد گزارش شده بود نیز بازتولید شد. سه اصلاح قبلی A05/A06/A10 همچنان برقرارند.

این گزارش ادعای یافتن تمام باگ‌های ممکن یا مشاهده سوءاستفاده روی سایت شما نیست. برای چنین اطمینانی، تست واقعی WordPress/WooCommerce، MySQL، مرورگر و بله لازم است. **در این دور کد اجرایی افزونه تغییر نکرد؛ فایل تست و گزارش اضافه شد. بله‌پی حذف‌شده باقی مانده است.**

گزارش قبلی با جزئیات A و B: [ممیزی ۲.۴.۰](AUDIT-2.4.0-fa.md). شناسه‌های D متعلق به این دور هستند.

## روش و شواهد

- بازاجرای مجموعه‌های قبلی و تست‌های باگ، به‌جای اکتفا به موفقیت lint.
- اجرای مستقیم کلاس‌های صف، اتصال مشتری، کانال، تنظیمات، لاگ و مسیریابی وبهوک با داده‌های مصنوعی؛ بدون HTTP واقعی یا اطلاعات مشتری.
- تزریق ترتیب اجرای مشخص برای دو رقابت هم‌زمانی. این روش نشان می‌دهد ترتیب معیوب در کد قابل وقوع است، اما اندازه‌گیری رقابت روی چند اتصال MySQL واقعی نیست.
- بازبینی خطاهای ذخیره، بازپخش فرم، تکرار مقصد، متن slashشده وردپرس، توکن داخل URL و تقدم دستورات ربات.
- بررسی سورس رسمی WooCommerce 9.0.0 برای جلوگیری از گزارش اشتباه درباره لینک HPOS.
- بررسی ۵۱ ثبت مستقیم hook با شکل `$this, method`؛ متد مفقود در این گروه پیدا نشد. این بررسی شامل تمام روش‌های پویا یا تأیید رفتار زنده نیست.

## ۱. یافته‌های تازه

### D01 — زیاد: قطع اتصال می‌تواند پیامِ خوانده‌شده از صف را متوقف نکند

**محل:** `balika/includes/class-bon-customer-store.php:128–141` و `class-bon-queue.php:93–130`.

worker ابتدا حداکثر ۲۰ ردیف را به حافظه می‌خواند. `unlink_chat()` اتصال و ردیف‌های منتظر را از دیتابیس پاک می‌کند، ولی با قفل worker هماهنگ نیست. worker پیش از ارسال، وجود ردیف یا اعتبار اتصال را دوباره بررسی نمی‌کند.

**ترتیب بازتولید:**

1. یک پیام مشتری وارد صف می‌شود.
2. worker نسخه آن را از دیتابیس می‌خواند.
3. پیش از تماس با API، قطع اتصال اجرا می‌شود؛ هم اتصال و هم ردیف پیام حذف می‌شوند.
4. worker از نسخه حافظه‌ای، متد ارسال را فراخوانی می‌کند.

**نتیجه تست:** دیتابیس خالی از اتصال و پیام بود، ولی یک ارسال ثبت شد. این با صرف «پیامی که قبلاً به API ارسال شده قابل پس‌گرفتن نیست» فرق دارد؛ در این ترتیب، API هنوز فراخوانی نشده بود.

**اصلاح پیشنهادی:** سیاست هم‌زمانی مشترک برای قطع اتصال و تحویل، بررسی مجوز/نسخه گیرنده در لحظه ارسال، و پیام رابطی که مرز واقعی توقف را توضیح دهد. حذف فیزیکی ردیف به‌تنهایی کافی نیست. قفل باید با تولیدکننده پیام هم هماهنگ باشد تا مسیر جدیدی برای رقابت ایجاد نشود.

### D02 — متوسط: رقابت ثبت انتشار کانال با worker باعث توقف بی‌دلیل می‌شود

**محل:** `class-bon-channels.php:64–86` و `class-bon-queue.php:103–107`.

در `dispatch()` ابتدا پیام با وضعیت `pending` درج می‌شود و سپس وضعیت برنامه به `queued` تغییر می‌کند. worker فقط وقتی ارسال را مجاز می‌داند که برنامه از قبل `queued` باشد. قفل برنامه و قفل worker یکی نیستند.

**ترتیب بازتولید:** درج پیام → اجرای worker پیش از ثبت متای برنامه → تشخیص برنامه هنوز `scheduled` و تبدیل پیام به `paused` → ادامه dispatcher و تبدیل برنامه به `queued`.

**نتیجه تست:** محتوای عمومی، مقصد و ماژول همه مجاز بودند، ولی برنامه `queued` و پیام `paused` باقی ماند؛ ارسال خودکار متوقف شد و به دخالت مدیر نیاز پیدا کرد.

**اصلاح پیشنهادی:** وضعیت میانی و بازیابی سازگار یا هماهنگی قفل/انتشار outbox؛ صرف جابه‌جاکردن دو خط نیز بدون بررسی خرابی بین مراحل کافی نیست. ترتیب قفل‌ها باید از ایجاد deadlock جلوگیری کند.

### D03 — زیادِ مشروط: ماسک‌کردن توکن داخل URL API ناقص است

**محل:** `class-bon-logger.php:33–35`؛ مسیر ورود متن خطای HTTP در `class-bon-api.php:50–54`.

regex ماسک توکن، قبل از ارقام به مرز کلمه `\b` نیاز دارد. در URL واقعی، توکن بلافاصله پس از `bot` قرار می‌گیرد؛ بین حرف `t` و رقم چنین مرزی وجود ندارد.

**بازتولید:** توکن مصنوعی با ساختار عددی متداول داخل `https://tapi.bale.ai/bot…/sendMessage` به `Logger::log()` داده شد و در متن ذخیره‌شده باقی ماند. تست کنترل نشان داد همان توکن به‌صورت مستقل ماسک می‌شود؛ مشکل مشخصاً به پیشوند URL مربوط است.

**شرط اثر امنیتی:** متن خطای HTTP، افزونه واسط یا خطای API باید URL/توکن را در خود داشته باشد. ادعا نمی‌شود همه خطاهای شبکه فعلی حاوی توکن‌اند یا توکن واقعی شما افشا شده است.

**اصلاح پیشنهادی:** حذف دقیق مقدار secret پیکربندی‌شده و توکنِ مسیر API پیش از ذخیره لاگ؛ فقط به یک شکل ثابت یا طول محدود token تکیه نشود. کلیدهای حساس دیگر نیز باید جداگانه پوشش داده شوند.

### D04 — متوسط: متن بعضی تنظیمات با بک‌اسلش اضافی ذخیره می‌شود

**محل:** `class-bon-settings.php:60–77,103–105,166,187–190`.

وردپرس داده POST را slash می‌کند. این فرم‌ها متن را بدون `wp_unslash()` به `wp_kses_post()` یا sanitizer می‌دهند. پاک‌سازی HTML به معنی برداشتن slash نیست.

**بازتولید:** متن `Customer's order` با شکل slashشده POST وارد handler واقعی تنظیمات شد؛ مقدار ذخیره‌شده حاوی `\'` بود. تست از sanitizer ساده‌ای استفاده می‌کند که مانند مسیر مربوط، unescape انجام نمی‌دهد؛ آزمون روی وردپرس زنده همچنان لازم است.

**اثر:** قالب، متن انبوه یا مقدار متنی دارای کوتیشن/بک‌اسلش می‌تواند با متن واردشده فرق کند؛ ذخیره‌های بعدی ممکن است آن را بدتر کنند.

**اصلاح پیشنهادی:** unslash دقیقاً یک بار در مرز ورودی، سپس اعتبارسنجی نوع و sanitize. مسیرهای import و عملیات جدید نباید دوباره unslash شوند؛ بعضی از آن‌ها همین حالا این کار را انجام می‌دهند.

### D05 — متوسط: پنل تنظیمات، شکست ذخیره را موفق اعلام می‌کند

**محل نمونه:** `class-bon-settings.php:65–66,77–78`؛ الگوی مشابه در چند شاخه ذخیره تنظیمات وجود دارد.

نتیجه `update_option()` بررسی نمی‌شود و notice موفقیت بدون شرط ساخته می‌شود.

**بازتولید:** دیتابیس مصنوعی نوشتن گزینه اتصال را رد کرد؛ مقدار جدید ذخیره نشد، ولی پیام موفقیت نمایش داده شد.

**اصلاح پیشنهادی:** مقدار نهایی ذخیره‌شده با مقدار مورد انتظار مقایسه شود. بررسی صرف `false` کافی نیست، چون `update_option()` برای مقدار بدون تغییر نیز `false` می‌دهد. برای هر فرم باید فرق «بدون تغییر» و «شکست ذخیره» روشن باشد.

این یافته با A06 فرق دارد: A06 ذخیره اتصال مشتری بود و اصلاح شده؛ این مورد ذخیره تنظیمات پنل است و هنوز باز است.

### D06 — متوسط: دستور صریح جست‌وجوی ربات ممکن است به مسیر تلفن برود

**محل:** `class-bon-webhook.php:164–176`؛ `class-bon-customer-store.php:36–64`؛ دستورات فروشگاه در `class-bon-commerce.php:207`.

`looks_like_phone()` با حذف تمام نویسه‌های غیرعددی تشخیص می‌دهد. مسیر پاسخ به تلفن پیش از مسیر دستورات فروشگاه بررسی می‌شود. بنابراین `/search 09121234567` به‌جای جست‌وجوی محصول، درخواست تلفن محسوب می‌شود.

**بازتولید:** پیام با همین دستور به handler واقعی وبهوک داده شد؛ handler تلفن فراخوانی شد و handler کاتالوگ اصلاً اجرا نشد. پردازش پایین‌دستی تلفن/فروشگاه در این تست stub است تا فقط مسیریابی سنجیده شود.

**اثر:** جست‌وجوی شناسه یا عبارت عددیِ مشابه موبایل به مسیر دیگری می‌رود. این به‌تنهایی اثبات افشای داده نیست؛ کنترل مالکیت تلفن موضوع جداگانه A01 است.

**اصلاح پیشنهادی:** تقدم دستورات صریح و محدودکردن تشخیص شماره به پیام واقعاً تلفنی، نه بیرون‌کشیدن ارقام از هر دستور.

## ۲. یافته قبلی B01 اکنون با تست قوی‌تر تأیید شد

**محل:** `class-bon-settings.php:164–180`.

سه سناریو اجرا شد:

1. تمام درج‌های صف شکست خورد، ولی پنل گفت برای **۲ مشتری** ثبت شده است.
2. دو شماره به یک chat متصل بودند؛ **دو پیام یکسان** برای همان chat ساخته شد.
3. همان POST دوباره پردازش شد؛ تعداد پیام‌ها از دو به **چهار** رسید.

پس علاوه بر شمارش نادرست، یکتاسازی مقصد و جلوگیری از بازپخش ناخواسته فرم لازم است. nonce وردپرس یک‌بارمصرف نیست و جای شناسه عملیات/idempotency را نمی‌گیرد. راه‌حل باید امکان ارسال عمدی کمپین بعدی با متن مشابه را همچنان حفظ کند.

## ۴. موارد مشکوکی که باگ قطعی حساب نشدند

برای جلوگیری از زیادکردن مصنوعی تعداد ایرادها:

- **لینک قدیمی ویرایش سفارش و HPOS:** در [سورس رسمی WooCommerce 9.0.0، PostsRedirectionController](https://github.com/woocommerce/woocommerce/blob/9.0.0/plugins/woocommerce/src/Internal/Admin/Orders/PostsRedirectionController.php#L124-L185)، redirect ویرایش CPT و `shop_order_placehold` وجود دارد. بنابراین در پیکربندی عادی آن نسخه، `post.php?...&action=edit` لزوماً خراب نیست. استفاده از API رسمی URL سفارش بهتر است، ولی خرابی قطعی اثبات نشده است.
- **تیک‌های لغو/مرجوعی در صفحه تجربه مشتری:** این وضعیت‌ها در آن صفحه عمداً از گزینه‌ها حذف شده‌اند و توضیح داده شده که از تنظیمات قبلی پیروی می‌کنند؛ گزینه بی‌اثر پنهان گزارش نشد.
- **نبود دکمه حذف کد در فرم گروهی:** خالی‌بودن کد عمداً از تغییر ناخواسته جلوگیری می‌کند؛ کمبود عملیات ابطال را نباید با لزوم حذف این محافظ اشتباه گرفت.
- **XLSX، چندمرسوله‌ای، API شرکت حمل، ورود/پرداخت بومی بله:** امکانات تکمیل‌نشده یا عمداً مسدودشده‌اند، نه اثبات وجود دکمه خراب. [برنامه مراحل ارسال](SHIPPING-PLAN-fa.md) همچنان مرجع است.
- **فایل `balika.zip`:** نسخه اصلی ۲.۲.۰ است؛ README همین موضوع را صریحاً اعلام کرده. با سورس فعلی یکسان نیست و نباید به‌جای بسته جدید نصب شود. آن را به‌عنوان تغییر مخفی یا خرابی بسته فعلی شمارش نکردم.

| فروشگاه React | bundle واقعی با پاسخ مصنوعی، checkout link، خطا و pagination | مرورگر/وب‌ویوی بله، نشست چندتب، cache، افزونه قیمت و محصول |
| گزارش/سبد رهاشده | مرور بازه‌ها، سقف‌ها، چرخه snapshot و پیام | کرون دیرهنگام، DST، سبد خرید واقعی و آزمون بار |
| فرم‌سازها/دیدگاه/یادداشت | hookها، فیلتر فیلد و مسیر پیام | نسخه واقعی هر فرم‌ساز، فیلدهای مرکب و حساس سفارشی |

### ریسک‌های باقی‌مانده که با این تست‌ها اثبات یا رد نمی‌شوند

- ارسال تکراری پس از موفقیت API و شکست checkpoint دیتابیس؛ تحویل exactly-once تضمین نشده است.
- اجرای هم‌زمان بررسی سبد رهاشده و بازگشت snapshot از `recovered` به `active` در ترتیب واقعی checkout.
- `GET_LOCK` در پیکربندی‌های متفاوت دیتابیس، object cache پایدار و وقفه بین درج صف و ثبت meta.
- درخواست‌های هم‌زمان تغییر سبد و تغییر نشست/ورود کاربر؛ اعتبار شرط‌های افزونه‌های محصول هنگام تسویه‌حساب.
- تأخیرهای شبکه در ارسال مستقیم اعلان‌ها؛ سرعت صف ۲۰ ردیف/قطعه در هر پنج دقیقه و خواندن یکجای مخاطبان انبوه.
- نمایش صفحات محافظت‌شده، cache/CDN، افزونه‌های امنیت و تفاوت قالب checkout.

## ۶. نتایج قابل تکرار

| آزمون | نتیجه |
|---|---|
| مجموعه اصلی PHP | **۱۹۲ بررسی موفق** |
| JavaScript معمول | **۷ تست موفق** |
| PHP ممیزی قبلی | **۱۱ مشاهده:** ۸ مشاهده باگ موجود + ۳ تأیید اصلاح قبلی |

| نحو PHP 7.4 | **۳۱ فایل بررسی شد** |
| وابستگی زمان اجرا | `npm audit --omit=dev`: **صفر مورد شناخته‌شده** |
| اتصال مستقیم hook به متد | **۵۱ مورد بررسی شد؛ متد مفقود در این الگو پیدا نشد** |

**موفقیت تست بازتولید یعنی باگ وجود دارد، نه اینکه رفع شده است.** این تست‌ها عمداً از runner عادی جدا هستند و هنگام اصلاح باید به assert رفتار صحیح تبدیل شوند. نتیجه dependency audit هم درباره منطق امنیتی افزونه یا وابستگی‌های توسعه نیست.

```bash
PHP_BIN=/path/to/php tests/run.sh
/path/to/php tests/audit-known-issues.php
/path/to/php tests/audit-deep.php
npm test --prefix commerce-ui
node --test commerce-ui/audit/known-issues.mjs
```

در محیط بررسی از `php-wasm-cli` به‌جای PHP بومی استفاده شد. transport، وردپرس و دیتابیس در تست‌های PHP شبیه‌سازی شده‌اند؛ jsdom هم مرورگر واقعی یا آزمون کامل وب‌ویوی بله نیست.
