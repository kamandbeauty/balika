# تحویل قابل پیگیری گزارش پایان روز

> به‌روزرسانی RC: اتصال سفارش‌محور و یکپارچگی گزارش هفتگی/موجودی پس از این گزارش اضافه شده‌اند؛ مرجع وضعیت فعلی و محدودیت‌های مهاجرت [راهنمای 2.5.0-rc.1](RC-2.5.0-fa.md) است. مطالب زیر سابقه مرحله قبلی را نیز شامل می‌شوند.

## مسیر استفاده

«بالیکا ← گزارش‌های روزانه»؛ لینک این صفحه در تب گزارش‌گیری هم موجود است.

برای هر روز، متن ثبت‌شده گزارش و وضعیت هر مقصد نمایش داده می‌شود:

- **ثبت صف ناقص:** گزارش ذخیره شده ولی درج مقصد در صف کامل نشده؛ اجرای بعدی تکمیل می‌کند.
- **در صف:** ارسال یا تلاش بعدی در انتظار worker است.
- **پذیرفته‌شده توسط API بله:** همه قطعه‌های پیام توسط API پذیرفته شده‌اند؛ نه اثبات دریافت/خواندن مدیر.
- **ناموفق نهایی:** پنج تلاش worker شکست خورده است.
- **متوقف:** گزارش روزانه/بله خاموش شده یا مقصد فعلی مجاز نیست.

پس از رفع مشکل، «تلاش مجدد همین مقصد» فقط همان ردیف ناموفق/متوقف را به صف برمی‌گرداند. ردیف موفق یا منتظر تغییر نمی‌کند. خاموش‌بودن گزارش یا حذف گیرنده با این دکمه دور زده نمی‌شود. تغییرات مقصد و فعال‌بودن گزارش هنگام تحویل دوباره کنترل می‌شوند؛ درخواست API که قبلاً آغاز شده قابل پس‌گرفتن نیست.

## ذخیره و بازیابی

۱. متن گزارش و مقصدهای یکتا در گزینه غیرautoload وابسته به روز ذخیره و نتیجه ذخیره بررسی می‌شود.
۲. هر مقصد شناسه پایدار وابسته به روز و مقصد دارد. درج صف زیر قفل مشترک worker انجام می‌شود.
۳. فقط پس از وجود ردیف صف همه مقصدها، تاریخ روز بعد ثبت می‌شود.
۴. اگر درج بعضی مقصدها یا دریافت قفل شکست بخورد، تاریخ جلو نمی‌رود و برای پنج دقیقه بعد بازیابی زمان‌بندی می‌شود. ردیف‌های موجود دوباره ساخته نمی‌شوند؛ حتی اگر یکی از آن‌ها پیش‌تر ارسال شده باشد.
۵. اجرای دوباره از همان متن ذخیره‌شده استفاده می‌کند، نه محاسبه تازه فروش. اضافه‌کردن مدیر جدید، گیرندگان گزارش قدیمی را گسترش نمی‌دهد.

اگر مقصدی تعریف نشده باشد، روز برای بازیابی باقی می‌ماند؛ پنل و لاگ به تنظیم مقصد راهنمایی می‌کنند. سابقه روزهای قبل از این قابلیت خودکار بازسازی نمی‌شود. ارسال دستی گزارش‌های بازه دلخواه نیز جدا از این سابقه است.

## محدودیت‌های صریح

- **تحویل دقیقاً یک‌باره تضمین نیست.** اگر API پیام را پذیرفته باشد اما پاسخ شبکه گم شود یا ثبت نتیجه در دیتابیس شکست بخورد، سیستم ممکن است در تلاش بعدی آن قطعه را تکرار کند. این محدودیت با شناسه داخلی به‌تنهایی حل نمی‌شود؛ API باید قرارداد idempotency قابل اتکا داشته باشد.
- صف فعلی هر پنج دقیقه بررسی می‌شود و گزارش بلند در قطعات ارسال می‌شود؛ گزارش در پایان روز آماده می‌شود ولی تحویل ممکن است چند دقیقه یا بیشتر پس از نیمه‌شب باشد. کرون واقعی برای اجرای منظم لازم است.
- گزارش بر اساس همان تعریف مالی قبلی افزونه و وضعیت سفارش هنگام ساخت snapshot است؛ این مرحله تعریف فروش/سود را عوض نمی‌کند.
- گزارش روزانه و ردیف‌های صف آن از پاک‌سازی ۳۰روزه مستثنا هستند. فعلاً تا حذف اختیاری داده‌های افزونه نگهداری می‌شوند؛ نگهداری متن و شناسه مقصد باعث رشد تدریجی دیتابیس می‌شود. بایگانی/حذف زمان‌دار با حفظ نشانگر عدم تکرار هنوز پیاده نشده است. صفحه سابقه ۲۰ روز در هر صفحه نمایش می‌دهد.
- به‌روزرسانی صف، snapshot و cursor تراکنش واحد نیستند؛ ترتیب پایدار و قفل‌ها برای بازیابی درج ناقص طراحی شده‌اند. بازیابی از خرابی دیتابیس، حذف دستی سابقه یا restore نامنطبق بکاپ تضمین نمی‌شود.
- این تغییر برای گزارش فروش روز کامل است؛ گزارش‌های ضمیمه موجودی و گزارش هفتگی به این outbox منتقل نشده‌اند.

## آزمون

۳۵۵ بررسی PHP و ۹ تست JavaScript موفق؛ شامل سناریوهای شکست ذخیره snapshot، درج جزئی، مقصد تکراری، ادامه پس از وقفه، حفظ متن، نتیجه مستقل دو مقصد، عدم ارسال مجدد مقصد موفق، پنج شکست و تلاش مجدد دستی، توقف و حذف مقصد، خرابی خواندن صف و عدم جلو رفتن تاریخ پیش از تکمیل صف.

تست‌ها شبیه‌سازی‌شده‌اند. رفتار MySQL چنداتصالی، توقف ناگهانی فرایند، کش پایدار، WordPress واقعی و API زنده بله هنوز در محیط staging آزموده نشده است. پذیرش تست‌ها معادل تضمین تحویل نیست.
