# سخت‌سازی امنیتی — مرحله اول

> به‌روزرسانی RC: اتصال سفارش‌محور و یکپارچگی گزارش هفتگی/موجودی پس از این گزارش اضافه شده‌اند؛ مرجع وضعیت فعلی و محدودیت‌های مهاجرت [راهنمای 2.5.0-rc.1](RC-2.5.0-fa.md) است. مطالب زیر سابقه مرحله قبلی را نیز شامل می‌شوند.

این مرحله اصلاح کد است، نه اعلام «همه ریسک‌ها رفع شدند». افزونه روی سایت‌های کاربر فعال بوده است؛ موارد زیر ریسک‌های لبه‌ای و کنترل‌های دفاعی‌اند، نه ادعای وقوع افشا یا سوءاستفاده واقعی.

## تغییرات

### ۱. حذف اطلاعات حساس از لاگ

- مقدار دقیق توکن فعال بات و secret وبهوک، همراه با شکل URL-encoded، پیش از ذخیره ماسک می‌شود.
- توکن داخل مسیر `/bot…/` حتی بدون مرز کلمه و پارامترهای `secret`/`token` ماسک می‌شوند.
- هنگام نمایش رکوردهای قدیمی هم پاک‌سازی اعمال می‌شود.

**محدودیت:** متن خام لاگ‌های قدیمی دیتابیس یا بکاپ‌ها بازنویسی نشده است. اگر احتمال ثبت secret واقعی وجود دارد، بررسی محدود و امن، پاک‌سازی سوابق و تعویض توکن/secret لازم است؛ تعویض secret به ثبت مجدد وبهوک نیاز دارد. ماسک‌کردن الگوها تضمین شناسایی همه اطلاعات حساس دلخواه نیست.

### ۲. قطع اتصال هماهنگ با صف

قطع اتصال مشتری اکنون همان قفل worker را می‌گیرد. اگر worker مشغول باشد، عملیات موفق اعلام نمی‌شود و مدیر/مشتری درخواست تلاش مجدد می‌بیند. پس از حذف اتصال، پیام‌های منتظر، ناموفق یا متوقف مشتری با وضعیت لغوشده نگهداری می‌شوند، نه حذف کور تمام پیام‌های همان چت. گزارش روزانه مدیر، کانال و صندوق پشتیبانی با قطع اتصال مشتری حذف نمی‌شوند.

اگر حذف اتصال یا لغو پیام شکست بخورد، نتیجه کامل موفق گزارش نمی‌شود. موفقیت حذف اتصال با امکان پس‌گرفتن درخواست شبکه‌ای که قبلاً شروع شده فرق دارد؛ چنین درخواست یا پیام تحویل‌شده‌ای قابل برگشت نیست.

### ۳. مجوز تحویل پیام سفارش

پیش از API برای انواع `customer_order`، `customer_status`، `customer_note`، `tracking` و `payment_reminder`:

- وجود سفارش و فعال‌بودن اعلان مشتری بررسی می‌شود.
- اتصال فعلی تلفن همان سفارش به همان چت دوباره بررسی می‌شود.
- یادآوری پرداخت فقط در صورت فعال‌بودن تنظیم آن و نیاز فعلی سفارش به پرداخت مجاز است.

مقصد حذف‌شده یا تغییرکرده و یادآوری سفارش پرداخت‌شده متوقف می‌شوند. این کنترل تازه **جایگزین اثبات مالکیت تلفن نیست**؛ ریسک A01 همچنان مستقل است.

### ۴. کلید بله

- `sendMessage` مستقیم هنگام خاموش‌بودن بله قبل از تماس شبکه رد می‌شود.
- worker در حالت خاموش پیام منتظر را ارسال نمی‌کند و آن را برای بعد نگه می‌دارد.
- callback تغییر وضعیت سفارش و گزارش دستی در حالت خاموش بله اجرا نمی‌شود.
- عملیات تشخیصی مانند getMe/ثبت وبهوک و پاسخ callback از این توقف sendMessage مستثنا هستند. خاموش‌کردن کلید، حذف مجوز مدیر یا قطع اتصال مشتری نیست؛ پیام منتظر ممکن است پس از روشن‌کردن دوباره پردازش شود.

## موارد مهم باز

1. **A01 — مدل اتصال تلفن‌محور:** لینک یک سفارش هنوز می‌تواند به نگاشت مشترک تلفن منتهی شود. باید اتصال سفارش‌محور و مهاجرت اتصال‌های قدیمی طراحی شود؛ هیچ ادعای رفع این مورد در این مرحله وجود ندارد. لینک سفارش به‌تنهایی تأیید مالکیت شماره تلفن نیست.
2. بازبینی مجوز تازه فقط برای انواع مشخص پیام سفارش اجرا می‌شود. پیام‌های قدیمی بدون نوع، ارسال‌های مستقیمِ خارج از worker و کمپین‌هایی که بعد از قطع اتصال با snapshot قدیمی مخاطب درج شوند هنوز نیازمند سیاست سراسری اتصال/نسخه مجوز هستند.
3. قفل مشترک worker/قطع اتصال به معنی قفل‌شدن همه تغییرات سفارش یا تنظیمات نیست؛ تغییر هم‌زمان سفارش پس از بررسی و هنگام درخواست API همچنان ممکن است.
4. متن صف snapshot قدیمی است؛ تطبیق اتصال فعلی، تاریخچه همه تغییرات شماره و متن را اثبات نمی‌کند. برای تضمین قوی‌تر، نسخه مجوز مقصد و مشخصات مرجع هنگام تولید پیام باید ذخیره شوند.
5. ریسک‌های قبلی هم‌زمانی کانال، زمان اعلان اولیه سفارش، تنظیمات concurrent و نسخه‌بندی دسترسی‌ها با این مرحله بسته نشده‌اند.

## آزمون

۳۷۱ بررسی PHP و ۹ تست JavaScript موفق؛ ۱۴ تست تازه اختصاصی سخت‌سازی به‌علاوه پوشش کلید اصلی در API واقعی افزونه و callback. بررسی نحو PHP 7.4 برای ۲۲ فایل includes موفق بود.

تست‌ها با DB/HTTP/WordPress شبیه‌سازی‌شده‌اند. قفل MySQL چنداتصالی واقعی، کش پایدار، مرورگر و API زنده بله باید در staging بررسی شوند. harnessهای تاریخی ممیزی ممکن است همچنان رفتار قدیمی را انتظار داشته باشند؛ آن‌ها runner اصلی نیستند.

## قدم امنیتی بعدی

اتصال سفارش‌محور: دسترسی حاصل از لینک هر سفارش فقط برای همان سفارش، عدم اتکا به تایپ شماره برای کشف سفارش‌های دیگر، و مهاجرت تدریجی/تأیید دوباره اتصال‌های قبلی. این تغییر باید همراه با مسیر روشن اطلاع‌رسانی مشتری و تست سفارش مهمان، حساب کاربری، HPOS و اتصال مجدد باشد تا قابلیت‌های فعلی بی‌برنامه مختل نشوند.
