# اصلاح مرحله دوم: انتقال مالک سفارش

## رفتار جدید

هر grant سفارش، `owner_hash` را نگه می‌دارد: هش شناسه حساب مشتری، ایمیل صورتحساب نرمال‌شده، کلید سفارش ووکامرس و نسخه تصادفی مالک. اطلاعات خام هویت در ستون grant ذخیره نمی‌شوند.

- تغییر شناسه مشتری، ایمیل صورتحساب یا کلید سفارش، grant قبلی را از نظر مجوز نامعتبر می‌کند.
- لینک اتصال نیز همان نسخه مالک را دارد؛ لینک صادرشده پیش از انتقال نمی‌تواند چت قبلی را به مالک جدید متصل کند.
- در ذخیره استاندارد WooCommerce، hook قبل از ذخیره هنگام تغییر این فیلدها نسخه مالک را می‌چرخاند. انتقال A→B→A، مجوز یا لینک A قبلی را دوباره زنده نمی‌کند.
- `/orders` فقط اتصال‌هایی را نمایش می‌دهد که هنوز با مالک فعلی سازگارند. صف پیام مشتری از همین guard استفاده می‌کند؛ ردیف قدیمی متوقف می‌شود.
- تغییر صرف آدرس، نام یا وضعیت سفارش اتصال را باطل نمی‌کند. تغییر ایمیل حتی برای اصلاح تایپی، محافظه‌کارانه نیازمند اتصال مجدد است. casing و فاصله پیرامونی ایمیل در هش نرمال می‌شوند؛ ذخیره تغییر واقعی فیلد ایمیل ممکن است نسخه را بچرخاند.

## ارتقا و اثر روی کاربران

ستون `owner_hash` به جدول سفارش‌محور اضافه می‌شود. marker مستقل schema فقط پس از مشاهده ستون ثبت می‌شود؛ شکست ایجاد ستون نباید مجوز قدیمی را معتبر کند.

هیچ grant قبلی با مالک فعلی خودکار تأیید نمی‌شود. ردیف‌های بدون hash و توکن‌های قدیمی که صرفاً order_id داشتند، نامعتبرند. مشتری باید از **لینک تازه همان سفارش** متصل شود. این محدودیت در پنل نیز توضیح داده شده است. سوابق قبلی حذف خودکار نمی‌شوند، اما مجوز نیستند. اتصال تازه پس از تطبیق نسخه مالک داخل قفل صف ذخیره می‌شود.

## مرز تضمین

این کنترل جای قفل اتمیک ذخیره سفارش و تحویل API نیست. سفارش ممکن است هم‌زمان پس از بررسی مجوز تغییر کند؛ درخواست شبکه قبلاً آغازشده قابل پس‌گرفتن نیست. کش/شیء سفارش در یک درخواست طولانی نیز باید در staging بررسی شود.

تغییرات استاندارد CRUD ووکامرس نسخه را می‌چرخانند. ویرایش مستقیم SQL که hook را دور بزند، برای تغییر جاری شناسه/ایمیل/کلید همچنان mismatch ایجاد می‌کند؛ ولی رفت‌وبرگشت مستقیم SQL یا restore هماهنگ هویت و epoch قدیمی می‌تواند حالت قدیمی را احیا کند. مدیریت بکاپ و انتقال مالک خارج از API ووکامرس نیازمند ابطال صریح/اتصال مجدد است.

این اصلاح شامل بازطراحی مجوزهای لینک موجود صفحه/ایمیل ووکامرس یا تضمین تازه درباره دسترسی شخص به خود آن صفحه نیست.

## اعتبارسنجی

۴۲۴ بررسی PHP و ۹ تست JavaScript موفق؛ ۱۷ بررسی به تعداد قبلی افزوده شده است. شامل انتقال حساب، تغییر ایمیل مهمان، تغییر کلید سفارش، رد توکن پیش از انتقال، برگشت مالک بدون احیای توکن قبلی، اتصال مجدد صحیح، رد grant بدون hash، عدم تأثیر تغییر آدرس/وضعیت و توقف واقعی worker پیش از transport است.

Harness ممیزی RC06 از انتظار افشای دسترسی به بررسی رد مجوز تبدیل شد. RC01 تا RC05 و RC08 و دو ایراد رابط همچنان در ممیزی باز هستند. این آزمون‌ها با WordPress/DB/transport مصنوعی اجرا شده‌اند؛ migration واقعی جدول، HPOS/CPT، کش پایدار و ذخیره هم‌زمان هنوز تست staging می‌خواهند.

بسته ZIP قبلی بازسازی نشده است. تغییر فعلاً در سورس پروژه است؛ قبل از ساخت نسخه بعدی تست زنده لازم است.
